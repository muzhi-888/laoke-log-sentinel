# 日志级别与异常分级

级别是巡检的第一道筛子。筛子孔开错了，要么淹没在噪音里，要么把真故障漏掉。

---

## 一、级别归一化对照表

各生态写法不同，比较前必须归一到统一集合。

| 归一后 | 各生态别名 |
|---|---|
| TRACE | `TRACE` `FINEST` `VERBOSE` `T` |
| DEBUG | `DEBUG` `FINE` `DBG` `D` |
| INFO | `INFO` `INFORMATION` `NOTICE` `I` |
| WARN | `WARN` `WARNING` `W` |
| ERROR | `ERROR` `ERR` `SEVERE` `E` |
| FATAL | `FATAL` `CRIT` `CRITICAL` `PANIC` `EMERG` `ALERT` |

### syslog 数字级别
`0=emerg 1=alert 2=crit 3=err 4=warning 5=notice 6=info 7=debug`。注意**数字越小越严重**，跟直觉相反。

---

## 二、级别的真实含金量（比定义更重要）

教科书定义人人会背，实战里级别的可信度是这样的：

| 级别 | 教科书定义 | 实战真相 | 巡检时怎么对待 |
|---|---|---|---|
| FATAL | 进程无法继续 | **含金量最高**，几乎不会误打。出现即真事故 | 无条件最高优先级，先看这个 |
| ERROR | 需要人工介入的失败 | **被滥用最严重**。业务校验失败、参数不合法、用户密码输错，全被打成 ERROR | 必须归并 + 看量级，不能一条一条看 |
| WARN | 潜在问题 | 有价值但被忽视。慢查询、重试、降级、连接重建都在这 | **重点看趋势**，WARN 量级突增往往是 ERROR 的前兆 |
| INFO | 关键流程节点 | 90% 是噪音，10% 是关键状态变更（启动/选主/配置加载/优雅停机） | 只在定位时间点时看，不做统计 |
| DEBUG | 排查用细节 | 生产环境本不该开。开着就说明有人忘关，本身就是个问题 | 生产日志里 DEBUG 占比高 → 记进报告，是配置问题 |

**推论一**：只筛 ERROR 会漏掉最有预警价值的部分。默认筛 `WARN,ERROR,FATAL` 三档。

**推论二**：ERROR 的绝对数量没意义，**ERROR 归并后的模板数量**和**单模板占比**才有意义。1 万条 ERROR 归并成 2 个模板 = 两个已知问题在刷屏；归并成 800 个模板 = 系统真的在崩。

## 三、无级别日志的级别反推

syslog、容器 stdout、裸文本没有级别字段。这类日志里恰恰藏着最致命的东西：

```
Sep  9 07:36:00 node-1 kernel[0]: No space left on device
2026-09-09T07:35:00Z stdout F Too many open files: /data/app/cache/seg-000123.idx
```

这两条一个 `error` 字样都没有，但比 90% 的 ERROR 都严重。

### 三层反推策略（按优先级）

**第一层：关键词命中**
```
FATAL 档：panic / fatal
ERROR 档：exception / error / failed / failure / refused / timeout / timed out
          异常 / 失败 / 错误 / 超时 / 拒绝
WARN  档：warn / retry / retrying / deprecated / slow / 重试 / 告警 / 慢查询
```

**第二层：故障特征库反推**（关键词没中时兜底）
用故障特征库匹配，命中 P0/P1 特征 → 判 ERROR；只命中 P2 → 判 WARN。这一层专门捞 `No space left on device` 这类「没有 error 字样但极严重」的日志。

**第三层：状态码反推**（access log）
```
5xx → ERROR    4xx → WARN    2xx/3xx → INFO
```
注意 404 大量出现可能是扫描器而非故障，401/403 成片出现要区分是凭证过期还是攻击。

反推出来的级别要**在报告里标注是推断的**，别跟原生级别混为一谈。人看报告时需要知道哪些是日志自己说的，哪些是工具猜的。

## 四、P0/P1/P2 分级：按「能不能自愈」切

级别说的是「日志作者当时觉得多严重」，分级说的是「你现在该多着急」。两回事。

### 判定标准

| 档 | 判定 | 特征 | 响应 |
|---|---|---|---|
| **P0** | 资源已耗尽，进程随时死；无法自愈 | 内存溢出、磁盘写满、文件句柄耗尽、进程被 OOMKill | 立即处理，其他问题多半是它的连带反应 |
| **P1** | 服务能力受损但没死；可能连锁扩散 | 连接池耗尽、超时、死锁、线程池打满、证书过期、DNS 失败 | 当班处理，注意扩散链 |
| **P2** | 单次请求失败，不影响整体 | 空指针、反序列化失败、鉴权失败、参数校验失败 | 排期修，但要看量级 |

### 三条判定纪律

**1. P0 优先，其余暂缓判断。**
磁盘写满会导致：日志写不进去 → 数据库写失败 → 连接不释放 → 连接池耗尽 → 请求超时 → 网关 502。你会在报告里看到 6 类故障，**根因只有 1 个**。先按 P0 处理，处理完重新巡检，80% 的 P1 会自己消失。

**2. 量级能改变档位。**
P2 的空指针一天 3 条 = 排期修；一小时 50 万条 = 事实上的 P0（日志刷屏会把磁盘写满，还会拖慢整个应用的 IO）。**分级看性质，优先级看性质 × 量级**。

**3. 新出现的比高频的更值得看。**
一个持续 3 个月每天 1000 条的 ERROR，和一个今天刚出现 50 条的 ERROR，**后者优先**。前者是已知的技术债（虽然该修），后者是变化，变化才对应「刚出的故障」。

对比方法：拿故障前一天同时段的日志跑一遍，做模板集合的差集。差集里的就是新增模板。

## 五、常见的级别使用反模式

在报告里点出来，比单纯罗列错误更有价值——这些是根因级的问题：

| 反模式 | 表现 | 后果 |
|---|---|---|
| 业务异常打 ERROR | 「用户名已存在」「余额不足」刷 ERROR | 告警疲劳，真故障被淹没 |
| catch 后既打日志又抛出 | 同一个异常在 3 层各打一次 | 一次故障放大成三倍日志量 |
| 循环里打日志 | 单请求打几百条 | 磁盘 IO 打满，日志比业务耗时长 |
| 堆栈打了但没上下文 | 只有 `NullPointerException` + 堆栈，没有订单号/用户 ID | 定位不到具体哪笔请求 |
| 打了上下文但含明文敏感信息 | 日志里出现完整手机号、身份证、token | 合规风险 |
| 生产开 DEBUG | DEBUG 占比 > 30% | 日志量暴涨，性能下降 |
| 级别硬编码 | 代码里写死 `logger.error`，无法动态调 | 出问题时想降噪都不行 |

发现这些，在报告的「下一步建议」里写清楚。修 5 个反模式，比修 50 条错误对系统的改善大得多。

## 六、级别筛选的实战配置

| 目标 | 建议筛选 | 理由 |
|---|---|---|
| 快速判断有没有大事 | `FATAL` | 有就是真事故，秒级得到结论 |
| 日常巡检（默认） | `WARN,ERROR,FATAL` | 兼顾预警和故障 |
| 故障定位 | `ALL` + 时间窗口收窄到 ±5 分钟 | 需要 INFO 里的状态变更来定位时间点 |
| 趋势对比 | `WARN,ERROR` 分别统计 | WARN 上升 + ERROR 平稳 = 恶化中还没爆 |
| 日志治理 | `ALL` + 看模板占比 | 找刷屏大户，砍掉噪音 |

**一个反直觉的经验**：定位故障时把 INFO 打开看。故障前最后一条 INFO 往往是「配置重新加载」「主从切换」「服务重启」——那才是真正的起点，而 ERROR 只是结果。
