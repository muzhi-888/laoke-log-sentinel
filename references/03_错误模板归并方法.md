# 错误模板归并方法

10 万条 ERROR 人是看不完的。但 10 万条 ERROR 归并完往往只有 20 个模板——这 20 个能看完。归并是日志巡检里唯一真正的降维手段。

---

## 一、为什么必须归并

同一个故障的日志长这样：

```
2026-09-09 07:32:00 ERROR order 100001 failed, cost 1203ms, node 10.2.3.4
2026-09-09 07:32:01 ERROR order 100002 failed, cost 987ms, node 10.2.3.5
2026-09-09 07:32:02 ERROR order 100003 failed, cost 1522ms, node 10.2.3.4
... 47000 条
```

直接 `sort | uniq -c` 得到 47000 个「唯一错误」，因为订单号、耗时、节点 IP 每条都不一样。归并后是 1 条：

```
order <N> failed, cost <SIZE>, node <IP>   × 47000
```

从「47000 个问题」变成「1 个问题出现 47000 次」——这才是能行动的信息。

---

## 二、占位化规则表

核心操作：把正文里的**变量部分**替换成占位符，只留骨架。

| 顺序 | 目标 | 占位符 | 说明 |
|---|---|---|---|
| 1 | 时间戳（`2026-09-09 07:32:50.123`） | `<TS>` | 必须最先，否则里面的数字被数字规则咬掉 |
| 2 | 时间戳（斜杠版 `2026/09/09 07:32:50`） | `<TS>` | 同上 |
| 3 | UUID | `<UUID>` | 结构固定，先抓走 |
| 4 | IP（含端口） | `<IP>` | 排在数字规则前 |
| 5 | URL（`scheme:/·/host/path` 形式） | `<URL>` | **必须排在路径规则前** |
| 6 | Windows 路径（`C:\...`） | `<PATH>` | |
| 7 | Unix 路径（`/a/b/c`） | `<PATH>` | |
| 8 | 邮箱 | `<EMAIL>` | |
| 9 | 十六进制（`0x7f8a...`） | `<HEX>` | 内存地址、错误码 |
| 10 | 长哈希（16 位以上十六进制） | `<HASH>` | traceId、sha、token |
| 11 | 单/双引号包裹内容 | `'<STR>'` / `"<STR>"` | 用户输入、SQL 字面量 |
| 12 | 带单位数字（`30000ms` `512MB`） | `<SIZE>` | 排在纯数字前，保留单位语义 |
| 13 | 千分位数字（`1,234,567`） | `<NUM>` | |
| 14 | 纯数字 | `<N>` | 最后兜底 |
| 15 | 连续空白 | 单空格 | 收尾，消除对齐差异 |

### 顺序错了会怎样（真实踩过的坑）

**URL 排在路径后面**（scheme 用 `S` 代指 http/https）：
```
输入: call upstream S:/·/pay.svc.internal/api failed
错误: call upstream S:/<PATH> failed     ← 路径规则先把 scheme 后面整段吃掉了
正确: call upstream <URL> failed
```
半截模板不但难看，还会让同一个错误因为 URL 长度不同而归并失败。

**纯数字排在时间前面**：
```
输入: at 2026-09-09 07:32:50
错误: at <N>-<N>-<N> <N>:<N>:<N>     ← 能用但丑，且跟其他数字混淆
正确: at <TS>
```

**规律**：**长的、结构强的先替，短的、宽松的后替。** 这跟正则的贪婪匹配是同一个道理。

## 三、归并粒度：粗了会掩盖，细了没用

占位化太狠 → 不同问题被并成一条：
```
过度归并: <STR> failed × 50000      ← 什么都看不出来
```

占位化太轻 → 归并不动：
```
归并不足: order 100001 failed × 1     ← 等于没归并
```

### 校准方法

一个经验判断：**归并后的模板数应该在 5 ~ 200 之间**。

| 归并后模板数 | 诊断 | 处理 |
|---|---|---|
| 1-2 个 | 归并过度，或者真的只有一个问题 | 抽 3 条样例人工看，确认是不是同一个问题 |
| 5-50 个 | 健康区间 | 直接看 Top10 |
| 200-1000 个 | 归并不足 | 检查有没有漏掉的变量类型（业务 ID 格式特殊？中文变量？） |
| > 1000 个 | 归并基本没生效 | 大概率是正文里有未识别的高基数字段，抽样看模板串找规律 |

### 保留 vs 抹掉的判断标准

| 内容 | 处理 | 理由 |
|---|---|---|
| 异常类名（`SQLException`） | **保留** | 这是分类的核心，抹了就没法归并了 |
| 表名、字段名 | **保留** | 定位到具体哪张表，有价值 |
| 方法名、类名 | **保留** | 定位代码位置 |
| 错误码（`ORA-00060`） | **保留** | 语义强，别当数字抹掉 |
| 订单号、用户 ID | 抹掉 | 高基数，无归类价值 |
| 耗时、大小 | 抹掉但**保留单位** | 用 `<SIZE>` 而不是 `<N>`，单位本身有语义 |
| IP、端口 | 抹掉 | 但如果怀疑单节点故障，需要**单独按 IP 分组统计一次** |
| traceId | 抹掉 | 但**保留一条完整样例**，后面要靠它去链路系统查 |

关键：**归并是为了看清全貌，样例是为了下钻定位**。每个模板必须保留至少一条完整原文样例，否则归并完就断线了。

## 四、堆栈的归并

带堆栈的错误更麻烦。两种策略：

### 策略 A：只用正文归并，堆栈存一份样例
适用大多数场景。同一模板下堆栈通常一样，存第一条即可。轻量、够用。

### 策略 B：正文 + 堆栈前 N 帧一起归并
适用于**同一句错误消息由多条不同调用路径产生**的情况。比如 `NullPointerException` 消息一样，但来自 5 个不同接口——这时候用正文归并会把 5 个独立 bug 并成一条。

取堆栈**前 3-5 帧**参与归并，且**优先取自家包名的帧**，跳过框架帧：
```
❌ at java.base/java.util.Optional.get(Optional.java:143)      ← 框架帧，无区分度
✅ at com.yourcompany.order.OrderService.pay(OrderService.java:88)   ← 这才是分类依据
```

判断哪些是自家帧：包名前缀白名单（`com.yourcompany.`），或反过来把 `java.` `javax.` `org.springframework.` `sun.` `io.netty.` 列黑名单。

## 五、模板的排序：次数不是唯一标准

按次数降序是默认，但只看次数会错过重要信息。四个维度都要看：

| 排序维度 | 揪出什么 | 什么时候用 |
|---|---|---|
| **次数** | 刷屏大户 | 默认，做日志治理 |
| **首次出现时间** | 新增的问题 | 故障定位（新出现的最可疑） |
| **时间集中度** | 突发型 vs 长期型 | 判断是新故障还是老技术债 |
| **严重度** | 致命但低频的 | 别让 1 条 OOM 被 10 万条 NPE 埋掉 |

**时间集中度**的算法很简单：模板的 `(last - first)` 时间跨度 ÷ 出现次数。跨度小次数多 = 突发；跨度大次数多 = 持续存在。

一个实战组合：**先看严重度 P0 的，再看首次出现时间最晚的，最后才看次数最多的。** 这个顺序找根因最快。

## 六、模板对比：找出「新增了什么」

这是巡检最有价值的一招，也最容易被忽略。

```
故障时段模板集合 A
基线时段模板集合 B（前一天同时段 / 上个版本）

A - B = 新增模板     ← 最可疑，故障几乎一定在这里
B - A = 消失模板     ← 也值得看：某个正常流程的日志不见了？
A ∩ B 且次数暴增     ← 老问题恶化
```

**基线怎么选**：
- 有周期性的业务（电商、支付）→ 用**上周同一天同一时段**，别用昨天（周末和工作日流量差几倍）
- 刚发版 → 用**发版前同样长的时间窗**
- 定时任务 → 用**上一次同一任务的执行时段**

基线选错，差集全是噪音。

## 七、归并结果的信任边界

归并是启发式的，不是精确的。三条必须承认的局限：

1. **模板骨架相同不代表根因相同。** `Connection is not available` 可能是 DB 挂了、也可能是慢 SQL 拖住、也可能是连接泄漏。归并给你的是「同一类现象」，不是「同一个原因」。

2. **占位化可能抹掉关键信息。** 如果错误的关键区别恰好在被抹掉的那个数字上（比如错误码），归并会掩盖问题。所以每个模板必须保留原文样例，且定论前回原始日志看上下文。

3. **高基数正文会归并失败。** 有些日志把整个 JSON 报文打进正文，每条都不一样,占位化也救不回来。这种要么按前 N 个字符截断归并，要么直接承认这条不适合归并、单独抽样看。

写在报告里的话：**模板是索引，不是结论。** 拿模板缩小范围，回原始日志下结论。
