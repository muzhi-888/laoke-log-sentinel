# 主流日志格式速查

巡检第一步不是找错误，是**先搞清这份日志长什么样**。格式没认对，后面全是垃圾进垃圾出。

---

## 一、七种格式的辨认特征

| 格式 | 一眼辨认 | 时间字段 | 级别字段 | 坑 |
|---|---|---|---|---|
| log4j / logback | `2026-09-09 07:32:50,123 ERROR [thread] logger - msg` | 有，毫秒用逗号 | 有 | 毫秒分隔符是 `,` 不是 `.`，很多解析器只认点 |
| JSON 行日志 | 每行一个完整 `{...}` | 键名不统一 | 键名不统一 | 键名有 8 种以上写法，见下表 |
| 容器 / k8s | `2026-09-09T07:32:50.123456789Z stdout F msg` | 纳秒精度 | **没有** | 纳秒超过 `%f` 的 6 位上限，必须截断 |
| syslog | `Sep  9 07:32:50 host proc[123]: msg` | **没有年份** | 没有（靠 facility） | 日期是 `%b %e`，单位数日期前面是两个空格 |
| nginx access | `1.2.3.4 - - [09/Sep/2026:07:32:50 +0800] "GET / HTTP/1.1" 200 123` | 有，独特格式 | 没有，看状态码 | 级别要从 status 反推 |
| Go 标准库 | `2026/09/09 07:32:50 msg` | 斜杠分隔 | 通常没有 | 日期用 `/`，别用 `-` 的正则去套 |
| 裸文本 | 什么都没有 | 没有 | 没有 | 只能靠正文关键词 + 特征库反推 |

### JSON 日志的键名混战

同一件事有多种写法，解析时要按优先级逐个试：

| 语义 | 常见键名（按出现频率） |
|---|---|
| 时间 | `time` / `timestamp` / `ts` / `@timestamp` / `eventTime` / `datetime` |
| 级别 | `level` / `lvl` / `severity` / `levelname` / `log.level` |
| 正文 | `message` / `msg` / `log` / `event` / `text` |
| 服务名 | `service` / `app` / `logger` / `component` / `kubernetes.container_name` |
| 链路 ID | `trace_id` / `traceId` / `X-B3-TraceId` / `dd.trace_id` |

级别的值也不统一：logrus 用小写 `error`，zap 用小写，Java 生态用大写 `ERROR`，syslog 数字级别用 `3`。**统一归一化再比较**，别直接字符串等值判断。

## 二、时间解析的四个真实陷阱

### 1. 毫秒分隔符
log4j 默认 `%d{ISO8601}` 输出 `2026-09-09 07:32:50,123`，逗号。Python `strptime` 的 `%f` 前面必须显式写 `,`：
```
"%Y-%m-%d %H:%M:%S,%f"   # 逗号版
"%Y-%m-%d %H:%M:%S.%f"   # 点版
```
两个都要备着，别赌。

### 2. 纳秒溢出
容器日志是纳秒：`07:32:50.123456789`。`%f` 只吃 1-6 位，第 7 位开始直接抛 `ValueError`。**先截断再解析**：
```python
s = re.sub(r"(\.\d{6})\d+", r"\1", s)
```

### 3. syslog 没年份
`Sep  9 07:32:50` 里没有年份。跨年日志（12 月 31 日 → 1 月 1 日）用当前年份补会算出「时间倒流」。补年份时的判断：如果补出来的时间比当前时间晚 1 天以上，减一年。

### 4. 时区混杂
一份日志里可能同时出现 `+0800`、`Z`（UTC）、无时区。**巡检只关心相对时序**，最省事的做法是统一剥掉时区后缀按本地时序处理；但如果要跟其他系统对时间，必须先转成同一时区，否则 8 小时的偏移会让你把上午的故障对到下午的发版上。

## 三、多行日志的合并规则

一条异常在日志里通常占 20-80 行。**不合并的后果**：一个异常被当成 80 条「错误」，统计彻底失真，Top1 永远是 `at java.base/...` 这种毫无信息量的帧。

### 续行的判定特征

| 语言 | 续行长相 | 判定正则要点 |
|---|---|---|
| Java | `\tat com.x.A.b(A.java:88)` | 以空白开头 + `at ` + 括号 |
| Java | `Caused by: java.io.IOException` | 行首 `Caused by:` |
| Java | `\t... 23 more` | `\.\.\.\s+\d+\s+more` |
| Java | `java.sql.SQLException: xxx` 独占一行 | 类名含包路径 + 以 Exception/Error/Throwable 结尾 |
| Python | `  File "app.py", line 12, in f` | 空格缩进 + `File "` |
| Python | `Traceback (most recent call last):` | 行首固定串 |
| Go | `\tgoroutine 12 [running]:` / `\t0x00007f...` | 制表符 + goroutine / 十六进制地址 |
| 通用兜底 | 4 个以上空格缩进 | `^\s{4,}\S` |

### 合并的两条纪律

1. **限制合并上限**（比如 40 行）。有些堆栈几百行，全存进内存会把巡检工具自己撑爆。
2. **续行判定不能太宽**。`^\s+\S` 这种一格空格就算续行，会把正常的缩进日志全吃掉。至少要 4 空格或明确的堆栈特征。

判断合并有没有做对，看一个指标：**条目数应该显著小于原始行数**。如果两者相等，说明堆栈完全没合并。

## 四、编码与文件读取

| 问题 | 表现 | 处理 |
|---|---|---|
| 编码混杂 | `UnicodeDecodeError` 中断 | `errors="replace"`，别让一个坏字节毁掉整次巡检 |
| Windows 中文日志 | GBK 编码 | 显式 `encoding="gbk"` 或 `cp936` |
| 行尾 | `\r\n` 残留 `\r` | `rstrip("\n").rstrip("\r")` |
| 文件太大 | 内存爆 / 跑很久 | 先 `--max-lines` 抽样看格式，再全量跑 |
| 多文件 | 轮转日志 `app.log.1` `app.log.2` | 通配符批量读，但**注意时间会乱序**，聚合统计不受影响，时间轴要重新排序 |
| 正在写入的文件 | 读到半截行 | 最后一行可能不完整，解析失败当正常情况处理，别报错 |

## 五、格式识别的顺序问题

多条格式规则会互相抢。**信息量大的、结构强的排前面**，宽松的兜底规则排最后。

典型的抢匹配：
- 「时间 + 级别」的宽松规则会把 `2026-09-09T07:32:50Z stdout F msg` 里的 `stdout` 当成级别 → 容器规则必须排在宽松规则**之前**，或者宽松规则要求级别必须是已知级别词。
- Go 的 `2026/09/09` 和 log4j 的 `2026-09-09` 分隔符不同，不会互抢，但都要单独一条。

工程上的自我保护：**级别认不出来时，把误认的那段还回正文**，别丢字。比如宽松规则匹到了 `level=blabla`，归一化后是 UNKNOWN，那就把 `blabla` 拼回 msg 开头，否则正文残缺，模板归并出错。

## 六、动手前的三分钟检查

拿到一份陌生日志，先做这三件事，比直接搜 ERROR 有用得多：

1. **看头尾各 20 行** —— 确认格式、时间范围、有没有多种格式混在一个文件里。
2. **数格式分布** —— 如果一份文件里 `plain` 占比很高，说明格式识别没覆盖到，先补规则再分析。
3. **数级别分布** —— 如果 ERROR 数量为 0 但你知道有故障，八成是级别字段没解析出来（无级别格式），要靠正文关键词 + 特征库反推。

这三步的产出直接决定后面结论可不可信。跳过它们出的报告，看着专业，其实是猜的。
