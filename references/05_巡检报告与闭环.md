# 巡检报告结构与闭环验证

报告不是把错误列一遍就完事。**一份能用的巡检报告，读完应该知道「现在该干什么」。**

---

## 一、报告的五段结构

| 段 | 内容 | 读者关心什么 |
|---|---|---|
| 0. 元信息 | 文件、条目数、时间范围、格式分布、级别分布 | 这份数据可不可信、覆盖了什么 |
| 1. 错误模板 Top N | 模板串、次数、级别构成、首末时间、原文样例、命中特征 | 有哪些问题、哪个量最大 |
| 2. 时间轴 | 按分钟/小时的错误量分布（带条形图） | 什么时候开始的、是持续还是脉冲 |
| 3. 突刺定位 | 异常桶 + 中位数 + 阈值 + 倍数 | 锚点在哪，去比对什么 |
| 4. 特征命中 | 故障类型 + 严重度 + 影响量 + 方向性假设 | 大概是什么问题、往哪查 |
| 5. 下一步建议 | 3-6 条可执行动作，带优先级 | 我现在该干什么 |

### 元信息段为什么放最前

因为它决定**后面所有结论的可信度**。三个必看数字：

- **时间可解析条数 / 总条目数** —— 比例低说明格式没认对，时间轴和突刺全不可信
- **格式分布里 plain 的占比** —— 占比高说明大量日志没被正确解析
- **级别分布** —— ERROR 为 0 但你知道有故障 = 级别没解析出来

这三个数字不对，报告直接作废，先修解析再谈分析。**跳过元信息看结论，等于闭着眼下判断。**

## 二、时间轴的四种形态与读法

时间轴是最容易被跳过、但信息量最大的一段。

```
形态一 · 持续型
07:30 ####
07:31 ####
07:32 #####
07:33 ####
→ 长期存在的老问题（技术债）。不是「刚出的故障」，别按应急处理。
→ 但要看有没有缓慢抬升——那是恶化的信号。

形态二 · 脉冲型
07:30 #
07:31 #
07:32 ##############################
07:33 #
→ 单点事件。去比对：发版记录 / 定时任务 / 上游流量突增 / 依赖抖动。
→ 三者之一大概率对得上。这是最好定位的形态。

形态三 · 阶梯型
07:30 ##
07:31 ##
07:32 ###########
07:33 ###########
07:34 ###########
→ 某个东西在 07:32 变了，之后一直是新水位。
→ 配置变更 / 发版 / 扩缩容 / 流量切换。查 07:32 前后 2 分钟的所有变更事件。

形态四 · 周期型
07:00 ####    08:00 ####    09:00 ####
07:30 #       08:30 #       09:30 #
→ 定时任务、缓存集体过期、整点批处理。
→ 找周期长度，再去 crontab / 调度平台里对号。
```

**读法纪律**：先看形态，再看数值。形态决定「这是什么性质的问题」，数值只决定「有多严重」。性质判断错了，后面全白费——把持续型老问题当应急故障处理，是最常见的浪费。

## 三、突刺检测：为什么用中位数而不是均值

### 均值 + 标准差的失效场景

```
数据: 1, 1, 1, 1, 1, 500
均值 = 84.2   标准差 ≈ 203
阈值 = 84.2 + 3 × 203 = 693
→ 500 检测不出来！因为它自己把均值和标准差都拉高了
```

这叫**掩蔽效应**：异常值污染了用来判断异常的统计量。故障场景下错误量动辄百倍，均值法基本失灵。

### 中位数 + MAD

```
MAD = median(|xi - median|)
阈值 = median + k × MAD × 1.4826
（1.4826 是让 MAD 与正态分布标准差可比的缩放常数）

同样数据: 1, 1, 1, 1, 1, 500
中位数 = 1   MAD = 0
→ MAD 为 0 时退化处理: 阈值 = max(中位数 × 2, 中位数 + 3) = 4
→ 500 ≥ 4，检出 ✅
```

**MAD 为 0 的退化处理很关键**。大部分桶数值相同时 MAD 就是 0，公式直接失效。这时候用「明显高于中位数」的简单判断兜住。

### 参数怎么调

| 参数 | 作用 | 调整方向 |
|---|---|---|
| `k` | 灵敏度 | 默认 3.0。噪音多调到 4-5；想抓小波动调到 2 |
| `min_count` | 绝对下限 | 默认 5。防止「中位数 0 → 出现 1 次就报突刺」 |
| 桶数下限 | 样本量 | 少于 4 个桶不做判断。3 个点谈不上分布 |
| 桶粒度 | 时间分辨率 | 定位用分钟，趋势用小时，长期用天 |

**桶粒度选错的后果**：按小时切桶会把 3 分钟的爆发平均掉，什么都看不出来；按分钟切一个月的日志会有 4 万个桶，噪音淹没信号。**先按小时找到大概时段，再按分钟切那一小段。**

## 四、下一步建议怎么写才有用

烂建议 vs 好建议：

```
❌ 「建议关注连接池配置」          —— 关注什么？怎么关注？
❌ 「排查内存溢出问题」            —— 废话，谁不知道要排查
❌ 「优化系统性能」                —— 完全不可执行

✅ 「先处理 P0 内存溢出：跑 jmap -histo:live <pid> 看对象数 Top20，
    确认是堆内泄漏还是缓存无上限。其他 3 类故障多半是它的连带反应。」
✅ 「以 07:32 这个桶为锚点，取前后各 5 分钟完整原始日志，
    看第一条异常出现在哪里，再比对该时段发版记录。」
✅ 「Top1 模板占了 47000 条（占总量 81%），先把它压下去，
    报告会瞬间干净一半，剩下的问题才看得清。」
```

**好建议的三个要素**：具体动作（跑什么命令 / 看什么文件）+ 判断标准（看到什么算什么）+ 为什么先做这个。

### 建议的生成逻辑

按这个优先级组装，别乱排：

1. **有 P0 → P0 排第一**，并说明「其他问题可能是它的连带反应」
2. **有突刺 → 给出锚点桶**，说明取前后多长的原始日志、比对什么
3. **Top1 占比过高（> 40%）→ 建议先降噪**，理由是「报告会干净一半」
4. **命中连锁组合 → 指出因果方向**（如超时 + 连接池 → 查下游）
5. **有重试风暴 → 提醒先关重试再定位**，否则现象被放大
6. **收尾必写闭环**：修完拿同一条命令再跑一次，比对模板数与突刺

第 6 条最容易被漏，但它是「巡检」和「闭环」的分界线。

## 五、闭环验证：修完必须再跑一次

没有验证的修复等于没修。

### 三个对比指标

| 指标 | 修好的样子 | 没修好的样子 |
|---|---|---|
| 目标模板次数 | 归零或降一个数量级 | 只降了 20-30%（改错地方了，或只治了一个分支） |
| 突刺 | 消失 | 还在，或时间点后移（只是推迟了爆发） |
| 模板总数 | 减少 | **增加了** —— 危险信号，修复引入了新错误 |

**模板总数增加**是最需要警惕的：说明修复动作本身带来了新问题。这时候要立刻看新增模板是什么。

### 验证的正确姿势

```
1. 记录修复前的巡检结果（存 JSON，别只看屏幕）
2. 修复上线
3. 等待至少一个完整业务周期（有定时任务的等到下一次执行）
4. 用完全相同的命令参数再跑一次
5. 对比 JSON：模板集合差集 + 目标模板次数 + 突刺
```

**参数必须完全一致**。级别筛选、桶粒度、时间窗长度任何一个变了，对比就没意义了。

**等待时长的判断**：
- 高频错误（每分钟都有）→ 等 10-30 分钟够了
- 低频错误（每小时几条）→ 至少等 2 小时
- 定时任务相关 → 必须等到下一次执行完
- 内存泄漏类 → 等一个完整的 GC 周期，别急着宣布修好

## 六、日志规范十条（治本的部分）

巡检做久了会发现：**大部分排查困难都是日志本身写得烂**。这十条改完，下次排查快一个数量级。

1. **一条日志一件事**，别把三个动作的结果拼成一行。
2. **带上业务标识**：订单号、用户 ID、traceId。没有标识的错误日志等于没有——你知道出错了，但不知道是谁的请求。
3. **异常必须带堆栈**，`logger.error(msg, e)` 而不是 `logger.error(msg + e.getMessage())`。后者丢掉了整个调用链。
4. **同一异常只在一处打日志**。catch 后既 log 又 throw，会让一次故障放大成三倍日志量，还制造「三个不同错误」的假象。
5. **业务异常不打 ERROR**。「余额不足」是正常业务流，打 WARN 或 INFO。滥用 ERROR 会造成告警疲劳，真故障被淹没。
6. **循环里不打日志**。要打就打汇总（「处理 1000 条，失败 3 条」），别打 1000 行。
7. **敏感信息脱敏**：手机号、身份证、卡号、token 一律掩码。这不只是合规问题，日志泄露是真实的数据泄露途径。
8. **时间戳带毫秒和时区**。没有毫秒无法排序高并发日志，没有时区跨系统对时会错 8 小时。
9. **正文用固定前缀 + 变量后置**，方便归并。`order create failed, id=123` 比 `订单 123 创建失败了` 好归并得多。
10. **级别可动态调整**。出问题时能临时开 DEBUG，问题过去能立刻关掉,不用发版。

在报告里点出违反的条目。**修 5 条规范，比修 50 条错误对系统的长期改善大得多。**

## 七、报告的信任边界（必须写在报告里）

三句话，一句都不能省：

1. **模板归并靠占位化，是启发式的。** 骨架相同不代表根因相同，定论前回原始日志看上下文。

2. **命中特征只代表方向，不代表根因。** 特征库给的是「这类现象通常由什么引起」，省的是「不知道从哪查」的时间，不是替你下结论。

3. **时间轴的可信度取决于时间解析率。** 元信息里「时间可解析条数」占比低时，时间轴和突刺结论全部作废。

把这三句放在报告末尾。**承认边界不会削弱报告的价值，反而是它能被信任的前提。** 一份把猜测说成结论的报告，用一次就没人信了。
