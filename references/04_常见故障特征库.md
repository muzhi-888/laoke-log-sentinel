# 常见故障特征库

每条 = 特征串 + 真实含义 + 排查动作 + 最容易误判的点。按严重度分档。

**用法纪律**：命中特征只说明「现象属于这一类」，**不等于根因**。特征库给方向，节省的是「不知道从哪查」的时间，不代替看上下文。

---

## P0 档：资源已耗尽，进程随时死

### 1. 内存溢出
```
OutOfMemoryError / Java heap space / GC overhead limit exceeded
Cannot allocate memory / MemoryError / fatal error: out of memory
OOMKilled / Killed process (dmesg 里)
```
**含义**：分不出内存了。但「哪种内存」决定了完全不同的处理路径。

| 具体串 | 是哪种 | 查什么 |
|---|---|---|
| `Java heap space` | 堆内 | 对象堆积、缓存无上限、大结果集一次load |
| `GC overhead limit exceeded` | 堆内且濒死 | GC 疯转但回收不掉，同上，更急 |
| `Direct buffer memory` | 堆外 | Netty/NIO 缓冲区泄漏，`-XX:MaxDirectMemorySize` |
| `unable to create new native thread` | 线程栈 | 线程泄漏，数一下线程数 |
| `Metaspace` | 元空间 | 动态类生成（CGLib/热部署）泄漏 |
| `OOMKilled` (k8s) | 容器超限 | 容器 limit < JVM 堆 + 堆外，limit 设小了 |

**排查**：先 `jmap -histo:live` 看对象数 Top20，再决定要不要 dump（dump 会 STW，生产要谨慎）。
**易误判**：容器里 `OOMKilled` 但 JVM 日志里没有 OutOfMemoryError —— 那是**堆外**或**容器 limit 设得比堆还小**，光调 `-Xmx` 没用。

### 2. 磁盘写满
```
No space left on device / ENOSPC / disk quota exceeded / 磁盘空间不足
```
**含义**：写不进去了。连带反应极广——日志写不进、DB 写失败、临时文件创建失败、连接不释放。
**排查**：
1. `df -h` 看空间
2. **`df -i` 看 inode** —— 空间还有但 inode 耗尽同样报 ENOSPC，海量小文件场景常见，这一步最容易被跳过
3. `du -sh /* | sort -h` 逐层下钻
4. 检查是不是**日志自己写爆的**（很常见，尤其错误刷屏时）
5. 检查有没有**已删除但句柄未释放的文件**：`lsof | grep deleted`，这种 `du` 看不到但空间不释放

**易误判**：以为清了文件空间就回来了。进程还持有已删文件句柄时，必须重启持有者或让它关闭句柄。

### 3. 文件句柄耗尽
```
Too many open files / EMFILE / socket: too many open files
```
**含义**：进程打开的 fd 数超过 ulimit。
**排查**：
1. `lsof -p <pid> | wc -l` 看当前数量，`cat /proc/<pid>/limits` 看上限
2. **按类型分组**：`lsof -p <pid> | awk '{print $5}' | sort | uniq -c | sort -rn`
   - `sock`/`TCP` 占大头 → 连接没 close（HttpClient/DB 连接泄漏）
   - `REG` 占大头 → 文件流没 close
3. `netstat -an | grep CLOSE_WAIT | wc -l` —— CLOSE_WAIT 堆积是最经典的连接泄漏信号

**易误判**：直接调大 ulimit 就算解决了。调 ulimit 只是把爆炸时间推后，泄漏还在。**除非确认是正常业务量增长导致的上限不足**，否则必须找泄漏点。

## P1 档：服务能力受损，可能连锁扩散

### 4. 连接池耗尽
```
Connection is not available, request timed out after 30000ms
HikariPool-1 - Connection is not available
Timeout waiting for idle object / pool exhausted / too many connections
获取连接超时
```
**含义**：池里没空闲连接了。三种可能，处理方式完全不同：

| 可能 | 判断依据 | 处理 |
|---|---|---|
| 慢 SQL 拖住连接 | DB 侧慢查询日志有货，池等待时间 ≈ 慢 SQL 耗时 | 优化 SQL / 加索引 |
| 连接泄漏 | 池使用率只升不降，重启后正常一段时间又爆 | 找没 close 的地方，开 `leakDetectionThreshold` |
| 池子真的小了 | 并发量 > 池大小，DB 侧压力正常 | 调大池，但先算 DB 最大连接数够不够 |

**排查顺序**：先看 DB 慢查询（最常见），再看池的活跃/空闲曲线，最后才考虑调参。
**易误判**：一上来调大 `maximumPoolSize`。如果是慢 SQL 引起的，调大只会让 DB 被更多慢查询压死，从「应用超时」变成「DB 崩」。

### 5. 请求超时
```
SocketTimeoutException / Read timed out / connect timed out
context deadline exceeded / ETIMEDOUT / i/o timeout / upstream timed out
```
**含义**：等不到响应。**必须先分清连接超时和读超时**：

| 类型 | 串 | 含义 | 查什么 |
|---|---|---|---|
| 连接超时 | `connect timed out` `ETIMEDOUT` | 三次握手都没成功 | 对端进程是否存活、端口是否监听、防火墙/安全组、网络可达性 |
| 读超时 | `Read timed out` `SocketTimeoutException`（连上后） | 连上了但对端处理慢 | 对端的耗时监控、对端是不是在 GC、对端下游是否也慢 |

**排查**：`nc -zv host port` 验证四层通不通，通 = 读超时问题，不通 = 连接问题。
**易误判**：把读超时当网络问题查半天。读超时基本都是**对端慢**，网络没毛病。

### 6. 连接被拒 / 连接重置
```
Connection refused / ECONNREFUSED / No route to host
connection reset by peer / ECONNRESET / Broken pipe
```

| 串 | 含义 |
|---|---|
| `Connection refused` | 对端 IP 可达但**端口没人监听**（进程挂了/没启/端口错） |
| `No route to host` | 网络层不通（路由/安全组） |
| `connection reset by peer` | 连上了但对端**主动 RST**——对端崩了、超过对端限制、或中间设备（LB/防火墙）掐了 |
| `Broken pipe` | 自己在往一个对端已关闭的连接写 |

**易误判**：`reset by peer` 当成网络抖动。它更多是**对端应用层主动断开**，去看对端日志比 ping 有用。

### 7. 死锁
```
Deadlock found when trying to get lock; try restarting transaction
deadlock detected / Found one Java-level deadlock
fatal error: all goroutines are asleep - deadlock!
```
**含义**：两个执行流加锁顺序相反，互等。
**排查**：
- DB 死锁：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`，能直接看到两条冲突 SQL
- Java 死锁：`jstack <pid>`，JVM 会直接打印 `Found one Java-level deadlock` 和涉及的线程

**处理**：**统一加锁顺序**（比如永远按主键升序加锁）。
**易误判**：靠重试兜住。DB 死锁重试确实能救单次请求，但根因不修就会一直发生，且高并发下重试会加剧冲突。

### 8. 线程池打满
```
RejectedExecutionException / Task xxx rejected from ThreadPoolExecutor
queue capacity full / worker pool exhausted
```
**含义**：拒绝策略生效了——上游提交速率超过处理能力。
**排查**：看**队列长度曲线**而不是线程数。队列一直满 = 处理能力不足；队列忽满忽空 = 上游有突刺。
**易误判**：盲目加线程。线程数超过 CPU 核数太多后，上下文切换开销反而降低吞吐。先查单任务耗时为什么高。

### 9. GC 长停顿
```
Full GC (Allocation Failure) 4.523 secs
Pause Full / GC pause 3200ms / allocation stall
```
**含义**：STW 时间过长，期间所有请求都在等——表现出来就是「上游大面积超时」。
**排查重点**：**先看 Full GC 频率，不是耗时**。
- 频率高（分钟级）+ 每次回收后老年代仍居高 → 内存泄漏，去 P0 第 1 条
- 频率低（几小时一次）+ 耗时长 → 堆太大或 GC 算法不合适，考虑调参/换 G1、ZGC

**易误判**：只调 GC 参数。如果是泄漏，调参只能把爆炸周期从 1 小时拉到 3 小时。

### 10. SSL / 证书问题
```
SSLHandshakeException / certificate has expired
unable to find valid certification path to requested target
x509: certificate signed by unknown authority / CERT_HAS_EXPIRED
```

| 串 | 含义 | 处理 |
|---|---|---|
| `certificate has expired` | 证书过期 | 换证书。**这种事只会在最忙的那天发生** |
| `unable to find valid certification path` | 信任链缺失 | 把 CA 证书导进 truststore |
| `certificate signed by unknown authority` | 同上（Go 版措辞） | 同上，或容器里缺 ca-certificates 包 |
| 握手失败无明确原因 | TLS 版本/加密套件不匹配 | 对端禁了 TLS1.0/1.1，客户端太老 |

**排查**：`openssl s_client -connect host:443 -servername host` 一条命令看有效期 + 信任链 + 协议版本。
**易误判**：容器里报证书错误就去查证书。经常是**容器镜像太精简没装 CA 根证书包**，跟证书本身无关。

### 11. DNS 解析失败
```
UnknownHostException / Name or service not known / EAI_AGAIN
no such host / Temporary failure in name resolution
```
**含义**：域名解析不出来。
**排查**：在**出问题的那个容器/主机里**执行 `nslookup <域名>`，别在自己机器上试。
**容器场景重点**：
- `/etc/resolv.conf` 的 `ndots` 配置会让短域名产生多次无效查询，拖慢甚至超时
- CoreDNS Pod 是否健康、是否被限流
- 是否配了 hostAliases 却拼错

**易误判**：以为是网络问题。DNS 挂了 IP 直连是通的，用 IP 试一下能立刻区分。

### 12. Redis 异常
```
JedisConnectionException / redis: connection pool timeout
READONLY You can't write against a read only replica
MISCONF Redis is configured to save RDB snapshots... / LOADING Redis is loading
CROSSSLOT Keys in request don't hash to the same slot
```

| 串 | 含义 | 处理 |
|---|---|---|
| `READONLY` | **连到从库了**，主从切换后客户端没刷新拓扑 | 检查 Sentinel/Cluster 配置，客户端要能感知切换 |
| `MISCONF` | **持久化失败**（磁盘满/权限），Redis 拒绝写入自保 | 去查 Redis 所在机器的磁盘 |
| `LOADING` | 正在加载 RDB/AOF，还没就绪 | 等，或检查为什么重启了 |
| `CROSSSLOT` | Cluster 下多 key 操作跨槽 | 用 hash tag `{user}:a` `{user}:b` 强制同槽 |
| 连接池 timeout | 同「连接池耗尽」 | 常见于大 key 阻塞，用 `--bigkeys` 扫 |

**易误判**：`READONLY` 当成权限问题。它是拓扑问题，改权限没用。

### 13. 数据库异常
```
SQLException / Duplicate entry 'xxx' for key 'yyy'
Lock wait timeout exceeded; try restarting transaction
Data too long for column / Table 'xxx' doesn't exist
max_allowed_packet / could not execute statement
```

| 串 | 真实含义 | 别弄错 |
|---|---|---|
| `Lock wait timeout` | 有**长事务**占着锁不放 | 不是死锁！死锁会立刻报错，这个是等到超时 |
| `Duplicate entry` | 唯一键冲突 | 高频出现说明**幂等设计有问题**，不是 DB 抖动 |
| `Data too long` | 字段长度不够 | 常见于新增了 emoji（4 字节）但字符集是 utf8 而非 utf8mb4 |
| `Table doesn't exist` | 表不存在 | 多环境时经常是**连错库**了，先确认连接串 |
| `max_allowed_packet` | 单条 SQL 太大 | 批量插入拆小批，别只调参 |

**Lock wait timeout 排查**：`SELECT * FROM information_schema.innodb_trx ORDER BY trx_started` 找最老的事务，它就是元凶。

### 14. 重试风暴
```
retry attempt 3/5 / retrying in 100ms / giving up after 5 attempts / 重试第 N 次
```
**含义**：本身不是故障，是**故障的放大器**。
**为什么危险**：下游变慢 → 上游超时重试 → 下游负载 ×3 → 更慢 → 更多重试 → 雪崩。多层架构里如果每层都重试 3 次，三层就是 27 倍放大。
**排查**：
1. 有没有**指数退避 + 抖动**（固定间隔重试会形成同步冲击）
2. 有没有**总次数上限**
3. 有没有**多层同时重试**（这是最致命的，只允许一层重试）
4. 是否对**不可重试错误**也在重试（参数错误、业务校验失败重试 100 次也没用）

**处理纪律**：定位其他故障前，**先把重试关掉或退避拉长**，否则现象被放大得看不清真相。

### 15. 限流熔断
```
429 Too Many Requests / RateLimit exceeded
circuit breaker is open / BlockException / FlowException / degrade
```
**含义**：请求被主动挡掉了。**先分清是自家配的阈值还是第三方给的**。
- 自家（Sentinel/Hystrix）→ 看是阈值设太低还是真的过载了
- 第三方 API 返回 429 → 看配额，**且往往是重试风暴打出来的**

**易误判**：以为熔断打开是坏事。熔断打开是**保护生效了**，真正要查的是它为什么被触发（下游慢/错误率高）。

### 16. HTTP 5xx
```
500 Internal Server Error / 502 Bad Gateway
503 Service Unavailable / 504 Gateway Timeout
```
**必须按码分开统计**，含义完全不同：

| 码 | 位置 | 含义 |
|---|---|---|
| 500 | 应用内部 | 代码抛异常了，去应用日志找堆栈 |
| 502 | 网关↔上游之间 | 上游进程挂了/连接被拒/响应格式非法 |
| 503 | 网关或应用 | 无可用上游（全挂/健康检查全失败），或应用主动返回过载 |
| 504 | 网关↔上游之间 | 上游超时，网关等不下去了 |

**易误判**：把 502 和 504 混谈。502 是「连不上/连上就断」，504 是「连上了但太慢」，一个查存活一个查性能。

### 17. 配置缺失 / 配置漂移
```
Could not resolve placeholder 'xxx' / missing required config
No such config / 环境变量未配置
```
**含义**：配置没读到。
**特征**：**发版当天最常见**，且往往只在某个环境出现。
**排查**：对比**目标环境与基线环境的配置差集**，一次就能找出来。别一个个 key 去猜。
**易误判**：以为是代码问题。配置类问题的代码在其他环境是好的，改代码方向就错了。

## P2 档：单次请求失败，看量级决定优先级

### 18. 空指针类缺陷
```
NullPointerException / TypeError: 'NoneType' object ...
invalid memory address or nil pointer dereference
Cannot read properties of undefined
```
**排查**：看堆栈**第一行自家包名的帧**，别在框架帧里找。Java 17+ 开 `-XX:+ShowCodeDetailsInExceptionMessages`，NPE 会直接告诉你哪个变量是 null。
**易误判**：加 null 判断就算修完了。要问「它为什么是 null」——多数是上游返回了空或配置没加载。

### 19. 反序列化失败
```
JsonParseException / JsonMappingException / Unrecognized field
JSONDecodeError / Unexpected token / cannot unmarshal
```
**含义**：上下游数据契约不一致。**多数是对端悄悄改了字段。**
**排查**：抓一条**原始报文**跟本地的模型定义对比，一眼就看出来。光看堆栈猜不出。
**易误判**：改自己的模型去适配。先确认对端是有意改的还是发错了。

### 20. 鉴权失败
```
401 Unauthorized / 403 Forbidden / invalid token / signature mismatch
AccessDenied / 权限不足 / 签名错误
```
**判断**：
- **成片同时出现** → 凭证过期 / 密钥轮换 / 签名算法变了（系统性问题）
- **零散出现** → 正常的用户侧行为（token 过期、权限确实不够）
- **签名错误** 特别要查**服务器时间偏差**，很多签名算法带时间戳，时钟不同步直接签名失败

**易误判**：把零散的 401 当故障。用户 token 过期是正常业务流，不该打 ERROR。

## 命中多条特征时的读法

真实故障几乎不会只命中一条。典型的连锁组合：

| 组合 | 读法 |
|---|---|
| 磁盘写满 + 连接池耗尽 + 超时 + 502 | **根因是磁盘**。修磁盘，其余三个自己消失 |
| 请求超时 + 连接池耗尽 | 下游变慢的连锁反应，从**下游依赖**查起 |
| GC 长停顿 + 大面积超时 | 根因在 GC，上游超时只是表象 |
| 重试风暴 + 限流 | 先关重试，限流是被自己打出来的 |
| 内存溢出 + 文件句柄耗尽 | 同一个泄漏的两个出口（连接对象既占内存又占句柄） |
| DNS 失败 + 连接被拒（同时段） | 基础设施层面事件，查网络/容器平台，别查应用 |

**通用读法：按严重度取最高的那条当锚点，时间上取最早出现的那条当起点。** 两者往往指向同一个东西——那就是根因。
